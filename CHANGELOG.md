# Changelog

All notable changes to this repository are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and releases follow [Semantic Versioning](https://semver.org/). The CLI, the server image and the Terraform module are released together from one `vX.Y.Z` tag.

## [Unreleased]

### Added

- `STACKORDER_SCHEDULER_CATCH_UP` sets how far a new scheduler leader looks back to catch up schedules missed while no instance was leading, a positive Go duration defaulting to `1h` and capped at `168h`. The scheduler already enqueues only the latest fire of each schedule in the window, so a window wider than an outage recovers the daily `stale_locks` (`08:00` UTC) and `sync_installations` (`04:00` UTC) jobs and each stack's latest drift fire without a burst of repeated work; a server down for longer than this window still drops those jobs until their next scheduled time. The default preserves the previous fixed one-hour look-back, so upgrading from v0.5.0 changes nothing unless the window is set; set it, for instance, to `26h` to recover a full day's maintenance and drift schedules on restart. Reachable through the Terraform module's `extra_environment`. See [Server configuration](docs/reference/server-configuration.md#scheduler-catch-up).
- `STACKORDER_SESSION_TTL` sets how long a browser session lasts, a Go duration between `5m` and `8760h`, defaulting to `168h` (7 days), the previous fixed lifetime. It fixes both the session cookie's `Max-Age` and the server-side `expires_at` at sign-in, so a change applies only to sessions created after it; existing sessions keep the lifetime they were issued with. See [Server configuration](docs/reference/server-configuration.md#variables).
- `STACKORDER_HSTS_MAX_AGE` adds a `Strict-Transport-Security` header to every response, with its value as the `max-age`, a positive Go duration of at least `1s` such as `8760h`. `STACKORDER_HSTS_INCLUDE_SUBDOMAINS` and `STACKORDER_HSTS_PRELOAD` (both `false` by default) add `includeSubDomains` and `preload`; `preload` requires `includeSubDomains` and a `max-age` of at least one year. The header is sent only when `STACKORDER_BASE_URL` is `https`, the same signal that marks the session cookie `Secure`; setting `STACKORDER_HSTS_MAX_AGE` with an `http` base URL, or the sub-settings without it, is a start-up error. It is off by default, so a self-hoster on plain HTTP or on a shared parent domain is not locked into HTTPS by an upgrade. See [HSTS](docs/reference/server-configuration.md#hsts) and [Security hardening](docs/operations/security-hardening.md#server).
- `STACKORDER_STATE_EXTERNAL_ID` (unset by default) sets the `sts:ExternalId` the server sends when it assumes [`STACKORDER_STATE_ROLE_ARN`](docs/reference/server-configuration.md#shared-outputs) to read [shared outputs](docs/configuration/outputs.md) state, so an operator whose state role lives in another account can require a matching external ID in the role's trust policy to guard against the confused deputy. It must be 2 to 1224 of the characters AWS allows in an STS external ID (letters, digits and `+=,.@:/_-`), and setting it without `STACKORDER_STATE_ROLE_ARN` stops the server at start. The external ID is an identifier, not a secret, and the server never logs its value; without it the role assumption is unchanged, so an existing deployment upgrading from v0.5.0 needs to do nothing. The Terraform module reaches it through the new `shared_outputs_external_id` input (`null` by default), which requires `shared_outputs_role_arn`. See [Security hardening](docs/operations/security-hardening.md#shared-outputs) for a trust-policy example.
- Terraform module: optional inputs to run on infrastructure you already have, each defaulting to today's behaviour so an existing deployment plans with no changes. `create_cluster` (default `true`) with `cluster_arn` runs the service in an existing ECS cluster instead of creating one. `capacity_provider_strategy` (default `[]`) runs the tasks under a capacity provider strategy, FARGATE and FARGATE_SPOT with weights and an optional base, in place of `launch_type = "FARGATE"`, which ECS forbids alongside it; at least one provider must have a positive weight, since ECS places no tasks when every weight is zero and an omitted weight is zero; for a cluster the module creates it associates the strategy's providers, an existing cluster must already have them. `database_secret_arn`, `app_secret_arn` and `metrics_token_secret_arn` (default `null`) make the module write each secret value, still with a write-only argument so nothing secret reaches state, into a Secrets Manager secret you own instead of creating `<name>/database-url`, `<name>/app` and `<name>/metrics-token`. An existing VPC was already supported through `create_vpc`, `vpc_id`, `public_subnet_ids` and `private_subnet_ids`; an existing database or load balancer stays out of scope. Upgrading from v0.5.0 moves the ECS cluster and the three secrets under `count` through `moved` blocks, so no resource is recreated and no state surgery is needed. See [Deploy on AWS](docs/operations/deploy-aws.md#existing-infra).
- An authenticated way to create, list and revoke API keys, so operators no longer insert rows into `api_keys` by hand. The new `stackorder-server api-key create|list|revoke` subcommand manages keys from a shell with `DATABASE_URL` set and needs no App credentials, so an operator mints the first key when none exists; `create` prints the secret once, and `--actor` (default `operator`) records the creator and the audit actor. Over HTTP, [`POST /v1/keys`](docs/reference/api.md#create-key) (`201` with the secret shown once), [`GET /v1/keys`](docs/reference/api.md#list-keys) and [`DELETE /v1/keys/{id}`](docs/reference/api.md#revoke-key) do the same for a caller that already holds a key. A key's name is trimmed and may be at most 100 characters, counted as Unicode code points and enforced the same way by the subcommand and the endpoint. Managing keys is administrator-only: a signed-in browser user is `403 forbidden` and a runner token `401`, so only an API key manages keys. Creating and revoking a key, by either route, is written to the audit log as `api_key_created` and `api_key_revoked`, each committed in the same transaction as the change it records, so a key never exists without its creation entry and a revocation is audited only when it takes effect; revoking an already-revoked key keeps the first revocation time and records no further entry. The secret is a SHA-256 hash at rest and never reaches the logs. There is no new migration and no new setting, and rows inserted into `api_keys` before this release keep working. See [API keys](docs/reference/server-configuration.md#api-keys).
- `stackorder-server migrate` applies the embedded migrations to `DATABASE_URL` and exits, for operators who migrate as a separate deploy step or from a one-off job instead of relying on the automatic migration at server start-up. It takes the same migration lock as start-up, so it is safe to run beside starting instances: they apply each migration once. It needs only `DATABASE_URL`, not `STACKORDER_BASE_URL` or the GitHub App settings. `stackorder-server migrate` applies every pending migration (exit `0`, printing the versions migrated, or `database already at version N`); `stackorder-server migrate --to N` stops at version `N` and refuses with exit `1` to move below the applied version or to a version that does not exist; `stackorder-server migrate --status` changes nothing and prints `current=`, `target=` and `dirty=` lines, exiting `0` when the database is up to date, `2` when migrations are pending and `1` when the database is dirty or ahead of the latest version the binary embeds, so `--status` and plain `migrate` agree on a database the binary cannot migrate up. Server start still migrates automatically, so an upgrade from v0.5.0 needs no new step; running `migrate` first is optional. Run it from the container image with `docker run --rm -e DATABASE_URL=… ghcr.io/stackorder/stackorder:X.Y.Z migrate`. See [Migrating](docs/reference/server-configuration.md#migrate) and [Upgrades and backups](docs/operations/upgrades-and-backups.md#server).
- A direct push to the default branch can now record its graph as the repository's default-branch graph, so the stack lists, [`GET /v1/overview`](docs/reference/api.md#overview), removed stacks and drift scheduling follow the default branch at once instead of waiting for the next merged pull request that had a plan. The new runner endpoint [`PUT /v1/repos/{owner}/{repo}/default-graph`](docs/reference/api.md#default-graph) takes the graph a push-triggered `resolve` job scanned and makes it the default-branch graph, reconciling `stacks.removed_at` exactly as a merged pull request's plan does. The server accepts it only from a GitHub Actions `push` token whose `repository`, `repository_id` and `ref` (`refs/heads/<default branch>`) are the repository's and whose `sha` is the graph's, and only while that commit is still the branch head, which it reads from GitHub under a per-repository lock; an out-of-order, superseded or force push, whose commit is no longer the head, records nothing (`recorded: false`), so an older push can never replace a newer graph. The `stackorder resolve` command records the graph instead of resolving a pull request when it runs on a push to the default branch. No server setting changes and no migration is added; recording nothing is the default until a repository adopts a `stackorder/actions` release that triggers the plan workflow on a push to the default branch (a follow-up, not in this release), so an existing deployment keeps the previous behaviour, where only a planned merge moves the default-branch graph. See [Workflows](docs/configuration/workflows.md#default-graph) and the [CLI reference](docs/reference/cli.md#resolve).
- `stackorder-server migrate --down --to N` reverts the schema down to version `N`, so an operator can roll back to an older release without restoring a snapshot when the migrations in between were additive. Before this release the server only migrated up and an older image refused to start on a newer schema, so going back meant restoring the pre-upgrade snapshot and losing every write since. Run it with the newer image, which embeds the down migrations the older one lacks; it is guarded — without `--yes` it prints the plan, the migrations it would revert and the data each one drops, and changes nothing, and only `--yes` reverts. It takes the same migration lock as start-up and warns to stop every instance of the newer release first, since a running one fails once the schema it uses is gone and the older release refuses to start until the schema is at or below the version it embeds. It refuses with exit `1` a target above the applied version, a `dirty` database, and a database ahead of the binary (whose migrations it cannot revert). Every embedded migration now has a tested down file, checked by a test that fails when one is missing and by up/down/up round trips on a populated database. This adds no setting and changes no default: automatic migration at start-up is unchanged and only ever migrates up. See [Migrating](docs/reference/server-configuration.md#migrate) and [Rolling back](docs/operations/upgrades-and-backups.md#rollback), which tabulates each release's schema version and what a downgrade loses.
- The server carries trace context across the work queue, so a webhook delivery and the worker that handles it, and a job and the worker that runs it, are one trace instead of two. When tracing is on (`OTEL_EXPORTER_OTLP_ENDPOINT` set), the W3C trace context of the request or job that queues a row is stored in a new nullable `trace_context` jsonb column on `events` and `jobs` (migration 0015), and the worker span is started as a child of that remote parent, sharing its trace id; a retry is a new child span under the same trace, and a span that begins long after its parent ended shows the queue delay. Log records written inside a span, the `http request` access log and the event and job handlers included, now also carry `trace_id` and `span_id`, so a log line joins its trace and, through the stored context, the request or job that queued the work. With tracing off nothing changes, and no log line gains the fields. Upgrading from v0.5.0 applies migration 0015, which adds a nullable column on populated `events` and `jobs` tables without rewriting them and needs no superuser; rows queued before the upgrade have no context and their worker spans stay root spans, and a server of this release and one of v0.5.0 keep running side by side during a rolling deploy, each inserting and claiming rows. Once 0015 is applied, a v0.5.0 server can no longer start against the database: its startup migration ends at 0009 and refuses a schema it does not recognise, so a rollback to the previous image, or a restart of a drained v0.5.0 replica, needs the pre-upgrade snapshot restored first. See [Upgrades and backups](docs/operations/upgrades-and-backups.md#server), [Metrics and tracing](docs/reference/metrics.md#tracing) and the [data model](docs/reference/data-model.md#queue-tables).
- Recovery from a migration that failed and left the schema `dirty`. The server and `stackorder-server migrate` now refuse a dirty database with an error that names the dirty version, says a migration did not finish, and points at the recovery, instead of the bare `Dirty database version N. Fix and force version.` from the migration library. The new `stackorder-server migrate --force N` records version `N`, clears the dirty flag and exits `0`, without running any migration; it only recovers a dirty database and refuses one that is not dirty (exit `1`), reading the dirty flag and recording the version in one locked operation so that a delayed, repeated or concurrent `--force` cannot rewind an already-recovered database, and it cannot skip migrations on a healthy schema. Each migration file runs in one transaction under the `pgx/v5` driver, so a migration that fails rolls back and leaves the schema at the version before it: after migration `N` fails use `--force N-1` and run `migrate` again to re-apply `N`, or `--force 0` for a failed first migration; force `N` itself only when you completed `N` by hand. This is a new subcommand and a clearer message only — there is no new migration or setting, and a database that has never had a failed migration is unaffected, so upgrading from v0.5.0 needs no action. See [Recover from a dirty migration](docs/operations/troubleshooting.md#dirty-migration) and [Migrating](docs/reference/server-configuration.md#migrate).
- `GITHUB_ENTERPRISE` (`true` or `false`, unset by default) forces whether the server is treated as talking to GitHub Enterprise Server, which decides the App manifest `/setup` offers. Until now that was inferred only from `GITHUB_WEB_URL`, so a server reaching github.com through a proxy or mirror whose web URL is not `https://github.com` was offered the Enterprise Server manifest, without the `deployments` permission and the `deployment_protection_rule` event. Set `GITHUB_ENTERPRISE=false` to keep the full github.com manifest in that case, or `GITHUB_ENTERPRISE=true` to request the Enterprise Server manifest even on `https://github.com`. Unset, the behaviour is unchanged: any `GITHUB_WEB_URL` other than `https://github.com` (case and a trailing slash ignored) is treated as Enterprise Server. See [Server configuration](docs/reference/server-configuration.md#ghes).
- Scoped API keys, so a key handed to a dashboard, a script or a support engineer need no longer be a standing administrator. A key may now be created **read-only** (refused every mutating route, enforced centrally by request method so even a route added later is covered), **installation-scoped** (sees only one installation — repositories, stacks, overview counts, runs, plan text, shared outputs, resources and the audit log — and treats everything of any other installation as `404 not_found`, with no `403`-versus-`404` existence oracle), and **expiring** (refused exactly like a revoked key once past its time, checked on every request). The scope flags are accepted by both `stackorder-server api-key create` (`--read-only`, `--installation <id>`, `--expires <duration>`) and [`POST /v1/keys`](docs/reference/api.md#create-key) (`read_only`, `installation_id`, `expires_at`), and are shown by `api-key list`, [`GET /v1/keys`](docs/reference/api.md#list-keys) and in the `api_key_created` audit entry. A scoped key is not an administrator: it can neither list, create nor revoke keys, so it can never obtain a broader key; only an unscoped read-write, installation-wide, non-expiring key manages keys, so a time-boxed key cannot mint a permanent one, and [`GET /v1/me`](docs/reference/api.md#me) reports `admin` accordingly. Migration `0016_api_key_scopes` adds the nullable `installation_id` and `expires_at` columns and `read_only` (default `false`) to `api_keys`; it is safe on a populated database and needs no superuser. Upgrading from v0.5.0 changes nothing for existing credentials: every existing key, and every row inserted by hand, stays an unscoped administrator that never expires, so no credential is narrowed or invalidated by the upgrade (only a `NULL` `installation_id` is unscoped — a hand-inserted `0` is a real, matchable installation scope). A scope is enforced only by a replica on this release, which stores a scoped or expiring key under the same hash v0.5.0 accepts while reading neither the scope columns nor the expiry, so during a rolling upgrade a still-running v0.5.0 replica honours such a key as a full, never-expiring administrator: mint and hand out scoped or expiring keys only once every replica runs this release, and revoke them before rolling back (see [Upgrades and backups](docs/operations/upgrades-and-backups.md#server)). See [API key scopes](docs/reference/api.md#api-key-scopes), [Scope a key](docs/reference/server-configuration.md#api-keys-scopes) and the [security model](docs/reference/security-model.md#human-access).

### Changed

- The CLI retries `429 Too Many Requests` from a rate limiter or reverse proxy in front of the server, which it failed on at once before, alongside the network errors, timeouts and 5xx answers it already retried, and honours a `Retry-After` header in either its seconds or its HTTP-date form on any retried answer, capped at one minute (a header asking for longer stops the retries). A `429` or 5xx that persists through the three retries is now *unreachable*, so `resolve`, `plan` and `drift` degrade to an `unconfirmed` result and `apply` fails closed (exit 3) where a `429` failed with exit 1 before. Upgrading needs no configuration: the attempt count, the 200 ms/800 ms/2 s backoff when no `Retry-After` is sent, and the 30 s per-attempt timeout are unchanged, and each attempt still requests a fresh OIDC token so a retry never replays one. See the [CLI reference](docs/reference/cli.md#server) and [Exit codes](docs/reference/exit-codes.md#server-answers).
- The documentation of `stackorder_runs_total` now says it counts each status a run enters, a transition count rather than a run count, and points at the new `stackorder_runs_created_total` for counting runs. The metric itself is unchanged.

### Fixed

- The `/setup` done page no longer tells everyone to require both the `stackorder/plan` and `stackorder/apply` checks in branch protection. Requiring `stackorder/apply` is right only where `apply.mode` is `before_merge`, the default; in `on_merge` mode the apply runs after the merge, so a required `stackorder/apply` check would block every merge. The page now states that condition, matching the [GitHub App reference](docs/reference/github-app.md#checks). The same correction is made in the README and the design notes, which gave the advice unconditionally.
- The CLI now removes a trailing slash from the OIDC token audience it derives from the server URL, matching the audience the server derives from `STACKORDER_BASE_URL`. A server URL written with a trailing slash (`--server`/`STACKORDER_SERVER_URL`, for example `https://stackorder.example.com/`) made every runner call fail with `401`, because the runner token's `aud` kept the slash while the server's expected audience had it removed. An explicit `STACKORDER_OIDC_AUDIENCE` is still sent as set, with only surrounding whitespace trimmed and any trailing slash kept, matching how the server reads it. No configuration changes; upgraded runners that previously needed a slash-free server URL now work either way.
- The `stackorder_github_rate_limit_remaining` gauge now carries an `installation` label and is absent until the first GitHub response, where before it was a single unlabelled series registered at `0`. GitHub's rate limits are per installation, and the App JWT has its own, so one unlabelled gauge mixed every budget and let one installation's remaining count overwrite another's; a value is now recorded per installation id, and under `installation="app"` for the App JWT. Requests made with a user access token (the sign-in flow) are not tracked. Because the series only appears once a response has been seen, it is no longer `0` on a freshly started, idle server, so the sample `StackorderGitHubRateLimitLow` alert no longer fires at start-up; that alert's expression becomes `min by (installation) (stackorder_github_rate_limit_remaining) < 500`. Upgrading from v0.5.0: a dashboard or alert that reads the unlabelled `stackorder_github_rate_limit_remaining` must select a label, for example `max by (installation) (...)` or `...{installation="app"}`. A series for a removed installation lingers until the server restarts. See the [metrics reference](docs/reference/metrics.md#github).

- A failing `.stackorder/hooks/post-apply.sh` now fails its stack instead of reporting it as applied. The apply itself still ran and its resources and state are still reported, but the CLI posts the result as `failure` with the hook's exit code and output, so the server records the stack as `failed`, blocks its dependents in later waves, does not dispatch them, keeps the run's orchestration locks held for a `before_merge` apply, and marks the run failed; the command still exits 1. Before this release a post-apply hook, typically a smoke test, failed the job's exit code but let the run continue and apply every dependent stack. This is a behaviour change with no setting: a post-apply hook that fails today with no consequence now blocks the stacks that depend on it. Server and CLI can still be upgraded in either order, since the result `status` values are unchanged: an older server already maps `failure` to a failed stack, and an older CLI keeps the previous behaviour. See [Hooks](docs/configuration/workflows.md#hooks).

### Added

- [Shared outputs](docs/configuration/outputs.md): a stack can read another stack's root-module outputs through the server instead of `terraform_remote_state`, so its role needs no access to the other stack's state object. The producer lists its readers under `outputs.readers` in `stackorder.yaml`, in its `.stackorder.yaml` or on an instance, as doublestar patterns over stack keys, or `owner/repo//pattern` for stacks of another repository of the same installation. The most specific level that sets `readers` replaces the others, `[]` withdraws a broader grant, and unset at every level the outputs are not shared, inside one repository too. The server reads the producer's `outputs` configuration from its default branch only, never from a pull request or a graph upload. Outputs marked sensitive are left out and named in `withheld` unless `outputs.sensitive` is `share`; the default, `withhold`, keeps them out of the consumer's saved plan and state.
- [`GET /v1/repos/{owner}/{repo}/stacks/{key}/outputs`](docs/reference/api.md#stack-outputs) serves a producer's outputs to the runner jobs of the stacks it lists, which name their run and their stack, and to API keys, which bypass `readers`; a session is refused. The server reads the producer's state object from S3 with its own AWS credentials, or through the role in `STACKORDER_STATE_ROLE_ARN`, and only when the object lies under an entry of `STACKORDER_STATE_BUCKETS` granted to the producer's repository. That variable, which turns the feature on, takes comma-separated `owner/repo=bucket` or `owner/repo=bucket/prefix` entries, or `*=bucket[/prefix]` to grant an entry to every repository; a prefix covers a key only at a path segment boundary, so `stacks/prod` does not cover `stacks/production/`. An apply or drift result whose state object no entry of its repository covers is accepted without recording the object and clears the stack's recorded location, so reads answer `409 state_location_unknown` instead of serving the object the stack left, and one repository cannot point its stacks at another repository's state unless the entries of the two overlap, which the server warns about at start-up; a read of such a location answers `403 state_bucket_not_allowed` before any request to S3, and is audited and logged. Unset, every read answers `404 outputs_disabled`. It decodes only the `outputs` block of a version 4 state and stops reading there, refuses state that OpenTofu encrypted, and stores, caches and logs nothing it reads. A reader in another repository gets `404 not_found` for every refusal of the producer or its policy, so the endpoint tells it nothing about which stacks exist, and an unlisted stack of the producer's repository gets `403 outputs_not_shared`. Every read, and every refusal after the server accepts the token or key, of the run, the producer, its policy or its state location, is recorded in the audit log as `outputs_read` or `outputs_refused`, with counts and never values. See [Server configuration](docs/reference/server-configuration.md#shared-outputs).

Its `stackorder_outputs` data source and ephemeral resource take the producer's key as `stack` and return `values` and `nonsensitive_values`, and the ephemeral resource keeps them out of the saved plan and the state. Inside a Stackorder job the provider needs no settings. Its publication to the Terraform and OpenTofu registries follows this release. See [Reading outputs in Terraform](docs/configuration/outputs.md#consumer).
- The scanner infers a `reads_state` edge with `source: stackorder_outputs` from each `data` or `ephemeral` `stackorder_outputs` block whose `stack` is a literal string, in a `.tf` or `.tf.json` file of a stack's directory or of a local module the stack calls, at any depth, so ordering, propagation and cross-repository dependents treat it as they treat `terraform_remote_state`. A key of the same repository must name a stack exactly, `owner/repo//key` adds the producer as an external stack, and a `stack` built from an expression infers nothing and warns to list the producer in `depends_on`. In a module, a `stack` that refers only to `var.<name>` values and calls no function takes them from the literal arguments of each `module` block that calls the module, one level up, and a block whose `stack` still names no stack warns, naming the module's directory, that only `depends_on` orders the stacks that call the module. Blocks in registry and git modules are not read, and `terraform_remote_state` is read only in a stack's own directory. An `ignore_inferred` entry for another repository that no such block reads is a warning. See [Ordering](docs/configuration/outputs.md#ordering).

The server records it from apply and drift results only, in new columns of `stacks` (migration 0008), as the [location](docs/configuration/outputs.md#state-location) it reads the stack's outputs from; a plan result or a graph upload never moves it. Terraform, OpenTofu and the hooks also get [`STACKORDER_SERVER_URL`, `STACKORDER_RUN_ID` and `STACKORDER_REPOSITORY`](docs/reference/cli.md#environment), each set even when empty, so a value inherited from the job never disagrees with what the CLI uses, and the provider can call the server from a stack's job.
- Terraform module: [`shared_outputs_state`](docs/operations/deploy-aws.md#shared-outputs), a list of buckets, each granted to one `repository`, or to every repository with `*`, with an optional key prefix and KMS key, sets `STACKORDER_STATE_BUCKETS` as `repository=bucket/prefix` entries and grants the task role `s3:GetObject` on the objects under each prefix, `s3:ListBucket` limited to the same prefixes, so that a missing object answers not found rather than access denied, and `kms:Decrypt` through S3 only; nothing in it can write or delete. `shared_outputs_role_arn` sets `STACKORDER_STATE_ROLE_ARN` and grants the task role only `sts:AssumeRole` on that role, whose own policies then grant the reads, for instance in the account of the state buckets. IAM grants the prefixes for every repository at once; the server's check keeps each repository to its own entries. The module refuses a repository that is neither `owner/repo` nor `*`, and a prefix with a `.` or `..` segment. Both are off by default, and `extra_environment` rejects the two variables.

### Changed

- The [local demo](docs/guide/local-demo.md) needs Docker, git and Terraform or OpenTofu, and no longer Go. The `server` profile of `docker-compose.yml` runs the published image, `ghcr.io/stackorder/stackorder` at the tag in `STACKORDER_VERSION` or `latest`, and the guide [installs the CLI](docs/guide/local-demo.md#cli) from the release archive after checking it against the checksums file. `--build` still builds the image from the checkout, and [From source](docs/guide/local-demo.md#from-source) keeps `make dev` and `make build-cli` for contributors.
- With shared outputs on, the server's AWS role, or the role in `STACKORDER_STATE_ROLE_ARN`, can read the whole state objects under the buckets and prefixes `STACKORDER_STATE_BUCKETS` lists, secrets included: IAM grants whole objects, and the filtering to outputs happens in the server. Each entry is granted to one repository, so a repository's jobs can make the server read only state under its own entries; within one repository, an apply, including a pull request's apply before merge, can point one stack at another stack's state under the same entries. A compromised server could then read those objects and the secrets in them, and answer reads with values of its choosing, though it still cannot write state. The [security model](docs/reference/security-model.md#shared-outputs) states the trade and the controls that bound it, [Security hardening](docs/operations/security-hardening.md#shared-outputs) has the narrow read-only role, and the README, `SECURITY.md` and the documentation qualify their claims that the server holds no cloud credentials and never reads state. A stack that reads shared outputs also calls the server from its plan, so that plan fails while the server is unreachable. Shared outputs are off by default, and the server logs once at start-up when they are on.
- Upgrade the CLI before adding `outputs` to a `stackorder.yaml` or `.stackorder.yaml`: older CLIs reject unknown keys, which fails the resolve job of every pull request. The reusable workflows install the latest release unless [`stackorder-version`](docs/configuration/workflows.md#inputs) pins one. A producer's outputs become readable once an apply or drift job on the new CLI has reported its state object; until then a read answers `409 state_location_unknown`, and a [scheduled drift check](docs/configuration/drift.md) records the object without changing anything.

### Fixed

- `make dev` waits until Postgres and LocalStack are healthy before it starts the server, which exited when its first connection reached a Postgres still starting, and `make down` also stops the server of the `server` profile.
- The local demo shows the `infra/` instances of `example-infra` in its graph output, its table of the example and its [scenarios](docs/guide/local-demo.md#scenarios), and no longer says the example's run workflow lacks `run-name`.
- A dispatched apply job, once bound, could report a result for a stack of a later wave that no dispatch carried yet, moving it to applied before its dependencies, and could record a named check on a stack the apply skips. The server now binds a job to a stack that no dispatch carries yet only through a dispatch of that stack's wave and environment, and to a skipped stack never. When a wave has several dispatches in one environment, it picks the one whose stacks the workflow run's jobs name, instead of the first unbound one, which could bind a job to a sibling chunk. A read of shared outputs binds a workflow run that no dispatch holds yet only when its jobs name a stack of the reader's dispatch. See [OIDC binding](docs/reference/api.md#oidc-binding).
- An `ignore_inferred` entry qualified with the stack's own repository, such as `acme/infra//stacks/prod/vpc` in `acme/infra`, suppresses the inferred `reads_state` edge to that stack, which it never matched before.

## [0.1.0] - 2026-09-30

The first release. It works with [`stackorder/actions`](https://github.com/stackorder/actions) v1.0.0 or later.

### Added

#### Wire types and configuration

- `api/v1` wire types shared by the CLI, the server, the UI and tooling, with JSON and YAML tags: stacks, edges, graphs, runs, run stacks, checks, matrix entries (with the checkout `sha`, `plan_run_id` and `artifact`), plan summaries, audit entries and the `v1.Error` codes. Stacks, affected stacks, run stacks, stack details and matrix entries carry their `instance`, and a stack its `watch_paths`.
- Loading, defaulting and validation of `stackorder.yaml` and per-stack `.stackorder.yaml`, with unknown keys as errors and per-stack merging.
- Stack instances. A key `path:instance` names one deployment of a directory, with its own state object, var files, environment variables, GitHub environment and apply role, and every instance is a stack of its own in the graph, affected sets, waves, locks, runs, checks, plan artifacts, drift and the UI.
- `stacks.instances.from_var_files` in `stackorder.yaml`, a glob relative to each stack directory: every matching file declares an instance named by its base name up to the first `.`, and is that instance's var file after the root and stack `var_files`. A derived name that is not a valid instance name is an error; a matched file an explicit `instances` list leaves out is a warning.
- `instances` in `.stackorder.yaml`, a list of names or a map from name to overrides of `environment`, `workspace`, `backend_config`, `var_files`, `env`, `plan_output`, `apply.allowed_teams`, `depends_on` and `ignore_inferred`.
- `backend_config` at the root, per stack and per instance: `-backend-config` values for `init`, as `name=value` or a file relative to the repository root. The scanner overlays them on the `backend "s3"` block, so inferred `reads_state` edges and the shared-state warning work for partial backends and per instance.
- `var_files` at the root, per stack and per instance: `-var-file` values for `plan`, the re-plan inside `apply` and `drift`, relative to the stack directory. A missing file is a scan warning and a plan error.
- `env` at the root, per stack and per instance: environment variables for the tool and the hooks, as a string or with a `plan`, `apply` and `drift` value, `drift` falling back to `plan`. Reserved names are refused, and values of secret-looking names are redacted.
- `stacks.exclude` in `stackorder.yaml`: directory globs that are never stacks, beating `stacks.discover` and `stacks.include`.
- `environments` keys `prefix`, `prefix:instance` and `:instance`, the most specific key winning, with template values.
- Go templates in `environments` values, `environment`, `workspace`, `backend_config`, `var_files`, `env` values, `depends_on` and `ignore_inferred`, with `.Path`, `.Name`, `.Instance` and `.Key`, the functions `trimPrefix`, `trimSuffix`, `base`, `dir`, `replace`, `lower` and `upper`, the builtins `and`, `or`, `not`, `eq`, `ne`, `lt`, `le`, `gt` and `ge`, and `if` and `with`. Other actions and builtins are refused, and output over 4096 bytes is an error, so a repository's configuration cannot stall the server.
- The environment of a stack is the first of the instance's `environment`, the stack's and the `environments` match that renders non-empty, then the instance name, then `default`.
- Validation of the instance keys: `environments` prefixes may not contain `:`, an empty prefix needs an instance part, and keys whose prefixes normalise to the same path with the same instance part are refused; a null item in `instances` or a null `env` value is refused; reserved `env` names and the instance name `default` are refused in any letter case; two `from_var_files` matches that derive the same instance name are an error.
- `depends_on` entries with an instance suffix; a bare path to a directory with instances resolves to the instance of the same name.

### Design deviations

Recorded in [ARCHITECTURE.md](ARCHITECTURE.md) and in the implementation notes of the design page on the documentation site.

- The CLI runs the repository hooks itself, in CI and locally, instead of the reusable workflow, and also sets `STACKORDER_PLAN_FILE`; `STACKORDER_PLAN_JSON` and `STACKORDER_PLAN_FILE` are file paths.
- `stackorder-run.yml` takes a fifth input, `sha`, the commit every job checks out; `mode` is `plan`, `apply` or `drift`, never `resolve`; `stacks` is required; the wrapper sets `run-name: stackorder ${{ inputs.mode }} ${{ inputs.run_id }} wave ${{ inputs.wave }}` so the server can bind the workflow run to its dispatch.
- Both reusable workflows require `server-url`, and the calling jobs must carry the permissions block, since a called workflow cannot raise permissions. The `plan.yml` resolve job also needs `pull-requests: read`.
- Server-dispatched `plan` and `drift` jobs run under the environment `default` and assume the plan role (`aws-plan-role-arn`, a new `run.yml` input); only `apply` dispatches carry the stack's environment. Every `run.yml` job runs under `environment: ${{ matrix.environment }}` in the concurrency group `stackorder-stack-<key>`. A stack with no environment mapping runs under `default`, never an empty name.
- The OIDC `sha` claim is never compared with the run's SHA. Plan runs are bound by `event_name`, the `refs/pull/<n>/merge` ref and the pull request head read from GitHub; dispatched runs by `workflow_dispatch`, the default branch ref, the dispatch's `run_id` and the environment.
- `apply.max_parallel` caps the number of stacks in one dispatch rather than concurrent jobs; the caller's `max-parallel` input limits jobs.
- `pull_request_target` plans are not supported; fork pull requests get a neutral check from the server.
- The CLI redacts with its own rules instead of a list of the runner's secret patterns.
- The implementation has more packages than the design names (`config`, `report`, `command`, `tf`, `client`, `principal`, `metrics`, `artifacts` and others), more run and stack statuses (`superseded`, `unconfirmed`, `unknown`, `skipped`), the `manual` trigger, and more API endpoints.
- The schema stores a stack's backend as one `backend` jsonb column and edges by `from_key` and `to_key`, keeps a ref-less family row per module, and adds tables for graph membership, checks, dispatches, OIDC `jti`s and the audit log.
